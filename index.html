What it actually was

The brief was “migrate WooCommerce.” What it became was determining the authoritative source of truth for every piece of product data. The legacy store, the inventory system, and the new database each turned out to be right about different things, and working out which was which shaped nearly every technical decision that followed.

Built for a paying client, on real domains, with live payments. Heavily AI-assisted — Claude Desktop drove a purpose-built MCP server for catalogue content, and design and code sessions ran through AI throughout. The interesting engineering was almost never the generation; it was the validators, constraints, and audits that decided which generated output was allowed to land.

01

Data migration and the SKU forensics problem

Did

Built a pipeline that pulled ~1,650 products off three legacy WooCommerce stores and audited every field against multiple sources — WooCommerce, Veeqo, the new database — to establish which one was authoritative for each piece of data. The pipeline is crash-safe end to end: checkpoints after every variation, resumable by diffing what is already saved, and atomic writes so a kill mid-json.dump() can’t leave a corrupted checkpoint.

From the notes

BikerShades variation SKUs follow a {modelBase}-{frameColor}-{lensType}-{strength?}-{suffix?} pattern, while parent SKUs carry WooCommerce dedupe junk (-0, -0-XT, -Master-MFB, -COMBOS) that must never be used to derive the real product SKU — deriving from the parent produced 200+ false duplicate flags. WooCommerce also groups genuinely different products under one listing: polarized (CAPL) versus non-polarized (CA), old versus revised SKUs. A “base SKU mismatch” check caught those, then immediately over-flagged legitimate combo products, where a single leading C is meaningful.

CPR29X36ST  vs  PR29X36ST     -> same family (combo prefix)
CAPL...     vs  CA...          -> different products
one normalization rule for a single leading "C":
  +12 products, +437 variations recovered

Veeqo was evaluated as a data source and rejected as one: coverage was ~99% for BikerShades, ~98% for Monster, but only ~10% for ProSport; qty_on_hand was populated on ~8% of rows, and there were 431 duplicate SKU rows with 162 genuine price conflicts. It became a gating check — is this SKU in active inventory? — and never an enrichment source. Items whose SKUs were absent from Veeqo entirely were flagged and excluded, overwhelmingly high-diopter bifocals and readers that had never been synced to marketplace inventory.

The two lines the notes state twice, independently: the project started as “migrate WooCommerce” and became “determine the authoritative source of truth for every piece of product data” — and WooCommerce’s only truly trustworthy artifact turned out to be SKUs, not the product data around them.

02

Payments — Stripe webhooks and two layers of idempotency

Did

Chose hosted Stripe Checkout Sessions over Payment Links or custom Elements — address validation, tax, 3D Secure, fraud, and PCI scope are exactly what the hosted page absorbs. Orders are created only in the webhook, never at checkout-session creation, with two independent idempotency layers and atomic Postgres RPCs for sales counters.

From the notes

layer 1  Stripe idempotency key   -> double-clicked checkout
                                     can't create two sessions
layer 2  DB unique constraint      -> the same webhook event
                                     delivered twice can't
                                     create two orders
RLS      orders / order_items are SELECT-only for
         authenticated; the webhook's service-role key is
         the only write path -> forged orders impossible
         via direct Supabase calls

Sales counting runs through atomic Postgres RPCs rather than read-modify-write, so concurrent webhook deliveries can’t lose an update. The refund lifecycle came later the same way: a refunded_cents column, a charge.refunded handler, and a decrement_total_sales_on_refund trigger with guard clauses so a repeat Stripe event can’t double-decrement. The status model was eventually cut down to three states — processing, shipped, refunded — with partial refunds derived rather than enumerated.

One deliberate simplification, recorded the same day it was made: no stock gating at checkout. Orders go through regardless and the owner refunds manually if something can’t be fulfilled — a correct call for a catalogue whose real stock signal lived in a system with ~8% coverage.

Later correctness passes caught the kind of bug that only shows up in production: an expired Stripe session being handed back to a user resubmitting a form, and customer_email being set from an unverified form field instead of the authenticated user’s actual email.

03

Frontend state — providers, streaming, and the auth-flash bug

Did

Built cart, bookmark, and auth state as a nested provider stack — AuthProvider → CartProvider → BookmarkProvider — with Map-based state and 800ms-debounced database writes, on top of Suspense-streamed category pages. State lives in the URL rather than React state wherever shareability and crawlability matter.

From the notes

Guest carts store only productId, variationId, and quantity in localStorage — never price, stock, or images, which always come fresh from the backend. The cart key is productSlug:sku end to end; the frontend and backend tracks converged on that composite key independently. A cross-brand pollution bug showed up early too: the bookmarks endpoint was missing its brand filter and was merging all three brands’ bookmarks into one list.

The best-documented bug of the project is the auth flash. Logged-in users saw “Sign In” for a beat on every page load before it flipped to their profile icon. The navbar was combining a server-accurate isSignedIn boolean with a client-side loggedIn flag that always started false and only became accurate after a useEffect ran. Two states had been used to model three.

- const [loggedIn, setLoggedIn] = useState(false);
+ const [loggedIn, setLoggedIn] = useState(null); // undetermined

- show = isSignedIn && loggedIn
+ show = isSignedIn && (loggedIn ?? true)

One line, no changes anywhere else, because null is falsy everywhere the flag was already read. It defers to the server’s answer until the client has one, and stays accurate afterwards — which is what makes the related case work too: a background cart-sync 401 mid-session no longer leaves the header claiming a signed-in state that has actually expired.

04

Try Before You Buy — kept outside the main cart

Did

Designed and shipped a complete BikerShades-only feature — seven deposit-tier packages, a three-step prescription intake with file uploads, Stripe checkout, admin fulfillment tooling with carrier and tracking, and customer-facing history on the account page — as its own flow rather than through the existing cart.

From the notes

The architectural call is stated plainly in the design notes: TBYB deliberately does not go through the existing cart, because adding nullable branching throughout cart code for one single-brand feature wasn’t worth the complexity.

The submissions table was redesigned two days after it was built, from FK-referenced to fully denormalized: a submission stores a complete snapshot of the package captured at submission time, with no foreign key back to the live catalogue at all. Historical submissions have to stay stable even if a package is later renamed, repriced, or deleted — drift-proof history over referential purity, consciously chosen for what is really a financial and fulfillment record. All 28 columns are NOT NULL, with optional fields sent as the literal string "None", so a missing field fails the insert atomically instead of writing a partial row.

duplicate prevention
  partial unique index on form_hash WHERE not paid
  + the genuine race: two concurrent requests hash
    identically -> catch the unique violation, loser
    reuses the winner's submission id

security
  role `authenticated` has NO insert grant on financial
  tables — a public anon key with insert would let anyone
  skip the route and write a spoofed price

Two smaller things worth keeping. File uploads were pulled out of React state entirely and fired only from an explicit user action, after a useEffect watching form state was found clobbering a URL that had just been restored from localStorage. And mobile uploads were failing silently until the cause surfaced: Next.js server actions cap request bodies at 1MB by default, while phone camera photos run 3–10MB.

05

Product copy for 882 products, via an MCP server

Did

Built a FastMCP server that Claude Desktop drives over stdio to generate descriptions and summaries for 882 products across three brands from their actual product photos — raw image bytes, so the copy describes what is visible rather than inferred specs. The loop is get_next_product → look at the image → generate → save_content, repeating until get_progress reports zero remaining.

From the notes

The interesting part is not the generation, it is the gate. save_content is a validator that returns VALIDATION FAILED and refuses the write.

save_content rejects:
  > 80 words
  raw measurements
  banned marketing phrases
-> caller must fix and retry; nothing partial lands

The rules were iterated on after catching the model inventing detail — calling plain-lens computer readers “blue-light blocking” because the image looked that way. That is the whole lesson recorded at the time: prompt instructions alone were not sufficient, so a code-level check went on top of them. The same instinct shows up again in the Rx frames catalogue, which was entered by hand from vendor screenshots rather than scraped, because Rx-specific detail needed human judgment — and two frames were dropped outright because their pages never stated an Rx range. Never assume, flag and skip.

A 16-check Python validator and an idempotent migration script carried that dataset in: 86 of 86 frames migrated, four brands.

06

Launch — domain cutover and a production data reset with no fallback

Did

Moved three live domains off WordPress and SiteGround onto Vercel — DNS records, SPF, DKIM, DMARC, Resend transactional email, branded auth email templates — enabled RLS across all catalogue tables, built a maintenance-mode kill switch specifically so a site could be taken down safely mid-cutover, flipped Stripe to live mode, and then reset and reimported the entire production database and Storage from scratch.

From the notes

During that reimport, all three original legacy WooCommerce sites turned out to have become partially unreachable since the original scrape. There was no fallback: the source of the images was gone, and the images had just been deleted.

Two properties of the pipeline, both decided months earlier for unrelated reasons, made the recovery possible. Image filenames are a deterministic pure function of the source URL — the full path after /uploads/, chosen back in May to avoid collisions from WordPress date folders. And Supabase Storage never deletes or re-encodes anything. So every filename was re-derived from the URLs in the raw JSON backups and every image re-downloaded byte-for-byte identical from Storage itself, instead of from the dead sites.

recovered  prosport     355 / 355
           monster      705 / 706
           bikershades 2224 / 2255
the two shortfalls were pre-existing 404s, not new losses
final verification: zero mismatches, every table, all brands

A day later a second, independent Supabase project was stood up as staging using the same pipeline, catching three environment-hygiene bugs on the way, and verified as an exact match with production across every table. One other launch-day detail worth naming: all 13 files using next/image were switched to native <img loading="lazy">, because Vercel’s image-optimization free tier was being exceeded across three deployments and images were failing to alt text.

Three storefronts on one codebase, plus the admin dashboard that runs them.

Appendix — nine phases

The chronological build, condensed from the session notes. Expand any phase.

1  ·  Migration pipeline kickoff May 27–31

bikershades.com turned out to be WordPress + WooCommerce with a public, undocumented Store API at /wp-json/wc/store/products — which reframed the job from “scrape a site” to “migrate a data source.” 647 products across 7 pages, then 6,064 variations across 486 variable products, fetched crash-safe with checkpoints.

Architecture decided here: three Next.js frontends sharing one backend, one MCP server, and one multi-brand-aware Supabase database, brand-aware from day one. Server-rendered rather than client-fetched, which ruled out GitHub Pages as a host.

Reliability lessons banked early: concurrency with ThreadPoolExecutor triggered mass 503s because the legacy server rate-limits by concurrent connections, not request rate — sequential was correct. Killing a script mid-write could corrupt a checkpoint, fixed with write-to-.tmp-then-os.replace(). An early image run used product slug instead of SKU for folder names and was restarted from clean rather than migrated.

First full end-to-end run: 581 products, 5,649 variations, 54 categories, all QA passing. 66 items parked for owner review across eight flagged buckets.

2  ·  Multi-brand migration and architecture Jun 1–7

Day one of this phase was an ops recovery: the ProSport WordPress install was crashing wp-admin on boot from a corrupted plugin, and rendering broken publicly from stale Elementor cache. No data loss — and getting it back up unlocked the WooCommerce admin REST API, which is what the rest of the summer used. The public Store API is lossy: one image per variation, binary stock.

Multi-brand config formalized down to one BRAND env var and a BRAND_CONFIG dict, so adding a brand is a dict entry rather than an edit across 28 files. Prices always integer cents. Reshape output field names deliberately match DB column names so verify scripts can diff by name with no mapping table.

Per-stage loss accounting: ProSport 171→154, Monster 277→255, BikerShades 704→562 — the heaviest loss, driven by Rx lens add-ons, admin and invoice line items, and duplicate-SKU listings. Junk-SKU filtering caught shipping labels, TBYB deposits, and Rx frames implemented as ordinary WooCommerce products; all three were flagged for rebuild as real app features instead.

3  ·  Migration complete, first live storefront, payments Jun 10–19

Migration completion, verified: 3 brands, 60 categories, 870 products, 3,108 product images, 9,633 variations, 2,085 variation images. A mid-run crash left a brand partially imported and the next delete hit an FK violation because live FKs lacked ON DELETE CASCADE — fixed with an explicit ordered delete cascade. Supabase’s direct Postgres hostname resolves to IPv6, which corporate networks block outright; the session pooler URL fixed it.

First working backend plus frontend on Vercel — the migrated data became a browsable storefront. Then Stripe Checkout went from decision to a fully idempotent payment pipeline in a day, and shipping addresses moved into Stripe’s hosted flow, removing the need for any address UI on the frontend.

The schema kept simplifying as it went: brand_id FKs dropped in favour of brand_slug text FKs, and stock/in_stock removed entirely since Veeqo owns that truth.

4  ·  Parallel backend and frontend build-out Jun 20–27

Thirteen endpoints deployed with a full test suite running against the live deployment. The category endpoint was rewritten to start from the junction table rather than products, matching the cheapest query plan.

One decision argued through carefully: public product URLs use brandSlug + slug for SEO even though id would be the fastest lookup — resolved with a composite unique constraint that is a correctness guarantee and a performance index at once.

Frontend build began mid-week and caught up fast: API client layer, the four-way error-page taxonomy, and the provider stack. Error handling got a systematic pass on both sides — validate params first, check DB errors explicitly, distinguish “not found” from real failure.

5  ·  Admin dashboard, refunds, design system Jul 1–8

The admin’s visual system was specified before any component code was written: large serif display type for page titles against small-caps monospace labels, an almost entirely black-and-white palette where colour is reserved strictly for semantic meaning, and thin-rule dividers instead of cards or shadows.

Two implementation details worth keeping. The categories page deliberately flattens the tree into a sibling array, because CSS Grid column alignment only works across direct siblings. And analytics bar fills represent each item’s share of the total rather than share of the leaderboard leader, so the chart shows true market share.

Product search needed a two-part query: simple products store SKU on the product row while variable products store it per variation, so the search fans out to both tables in parallel and unions the results.

6  ·  Admin product management, TBYB launch Jul 15–31

Full create/edit product flow, covering simple and variable products, image uploads, colour-picker attributes, category tags, and sale pricing. Product UUIDs are pre-generated client-side so images can upload before the product row exists.

A real known gap was documented rather than hidden: images, categories, and description images use a delete-all-then-reinsert pattern on save, which is not atomic. A confirm-before-write modal was added to reduce the blast radius of an accidental save.

Auth work landed alongside: the full sign-up, sign-in, PKCE-based reset and email-confirmation flow, moved to custom SMTP via Resend to get past Supabase’s free-tier email rate limit. Then TBYB design, build, and its snapshot-schema redesign.

7  ·  TBYB productionization Aug 1–7

React port, then Stripe checkout with form hashing and the partial unique index, then admin fulfillment tooling with carrier and tracking — whose save and undo logic keys off persisted DB state rather than the draft — then account-page history, then mobile and localStorage polish.

The seven real deposit packages were seeded here: BikerArmour, Wiley X, 7Eye, and their bundles, $229–$349. The auth-flash fix landed the same week as a side quest.

8  ·  Rx prescription frames Aug 10–14

Veeqo order creation was wired into the Stripe webhook, awaited rather than backgrounded — Vercel kills a serverless function the moment it responds, so un-awaited work after return isn’t reliable. A genuine Veeqo double-POST race was solved with an atomic conditional UPDATE that lets exactly one concurrent invocation win the right to sync. Testing also revealed Veeqo’s API shape uses sellables, not variants.

The Rx client component separates “which frame’s form is open” from “which swatch is clicked” from “mouse-over display only,” with the selected colour derived rather than stored, specifically to avoid state-sync bugs. A PD validation bug was fixed here too — it had been wired to the wrong step, letting a customer advance without entering required values.

The hard part of the Rx order endpoint was deposit double-spend prevention: a TBYB deposit can be applied to a later Rx order, computed at read time, and it took three iterations of session-claiming logic before concurrent requests were provably safe.

9  ·  Final polish and production launch Aug 16–24

Rx order flow finished with pricing computed server-side from fixed price maps so the client can never manipulate cost, admin tooling mirroring the TBYB pattern, and customer-facing Rx history. A delete-account flow, footer and legal copy, and a cluster of Stripe correctness fixes closed out the polish.

One bug caught just before launch would have broken production signup outright: confirmation-email links were falling back to the raw .vercel.app preview URL instead of the real domain.

Then the cutover, live Stripe, the maintenance-mode switch, the full production reset and reimport, and a staging environment mirroring it exactly a day later.
